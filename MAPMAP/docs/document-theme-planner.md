# Document theme planning

The town workspace has an explicit input selector: **Theme prompt** or **Scenario / planning DOCX**. Both use the existing town vision pipeline. Prompt mode sends no document or reviewed requirements; document mode requires an uploaded DOCX and accepts scope instructions. Switching modes clears the uploaded document, requirements, prompt and previous plan selection to prevent cross-mode leakage. Mode selection is disabled during planning/generation. Crypt retains its existing prompt-only route.

The town style workspace accepts a DOCX document up to 64 MB alongside a user instruction. Input format is free; the reader extracts paragraph text, including table cells, with stable paragraph IDs. Embedded images are analyzed with nearby text before planning; see [document image ingestion](document-image-ingestion.md) for scope and limits. External links are not fetched. Multimodal model observations remain fallible and require review.

The existing isolated-object recognition and exact-pixel deduplication remain unchanged. A per-object LLM Planner selects document evidence, attached decoration commands, optional object-specific palette settings, and deferred requirements. Evidence IDs must resolve to source paragraphs. Applied object changes without evidence are rejected. The output includes source quotations for human review; valid IDs do not prove semantic correctness.

The document is first normalized into English requirements with target kinds and operations (`color`, `decoration`, `state`, `deferred`). Only object-specific color and decoration requirements are passed to the object Planner; global atmosphere is handled separately. The workspace exposes the normalized requirements as editable JSON. Editing invalidates the previous generation selection; analyzing again creates a new plan marked as reviewed input, without overwriting the original automatic experiment. Evidence audits include nearby source paragraphs to help detect section-scope errors.

Earlier local Halloween pilots used reviewed document-derived fixtures. Those private fixtures are not distributed as production theme logic or proof of fully automatic interpretation. Automatic normalization can still confuse section scopes, and model evidence audits are not reliable enough for unattended whole-map application.

Global color inference receives only global color/state requirements; tree-specific palettes are not inputs to building colors. If an object has only a color operation, generated Add sentences are saved as `discarded_commands` and never executed. Color-only edits have a separate semantic audit prompt. `scripts/check-document-tree-pilot.py` runs an isolated, logged color-only preview without FLUX or map application.

Decoration plans specify `placement`: ground, wall, roof, object_surface or none. The DSL compiler adds placement-specific constraints and preserves doors, windows and flower boxes. Ground props are small and placed at the base, not painted on walls. This is a language constraint, not a guaranteed spatial mask: generated images still require geometric and visual validation. Source-alpha clipping remains conservative and may omit freestanding decorations outside the source silhouette. Registration thresholds are unchanged; rejected affine transforms now save structured native-pixel displacement diagnostics in `extraction-failure.json`.

The town planning endpoint optionally accepts representative `targets` for small experiments; unknown or duplicate IDs are rejected. This does not change source object grouping or game placement. For document plans, the global direction model's speculative decoration list is cleared: only audited object commands request decorations.

## Fixed pixel style

All requests through the shared FLUX/Comfy image request path append the `native-pixel-v1` style contract: 2D pixel-game sprites, reference grid/perspective, limited flat shading and no photorealism, 3D, blur or smooth gradients. The exact effective prompt and policy version are logged. Document DSL already includes this contract; the request wrapper is idempotent.

Town decoration overlays are resized with nearest-neighbor sampling, quantized to at most 24 colors without dithering, and use binary alpha. This applies only to generated decorations, never original sprites or original alpha. These technical properties do not prove aesthetic/style compatibility; visual review still gates application.

`POST /town-vision/ground-prop-pilot` accepts a reference plan ID, 32x32 reference asset and a short requested prop description. It shares the generation lock and preserves source hashes. The building is not sent for repainting. Generated backgrounds must be flat and the foreground must be a single isolated component. The extracted sprite fits a 32x32 canvas with a bottom-center anchor, a 24-color palette and binary alpha. Raw outputs, timing and validation are saved. This experimental route has no automatic game-application path; map coordinates, occlusion and visual quality must be reviewed separately.

The final decoration DSL is the actual FLUX prompt: fixed preservation constraints plus up to three short English `Add` commands. A second LLM evidence audit checks commands and color overrides against quoted paragraphs; a failed or missing audit blocks generation. This model audit is fallible and does not replace human review. Original color and brightness changes use code, not FLUX. Geometry changes, new assets, layout changes and gameplay belong to deferred work. Source validation, experimental decoration extraction and explicit visual approval still gate application.

Plans persist document text, limitations, model responses, source hashes, per-object plans and prompts under the existing local theme-runs store. Child runs copy document provenance. Do not publish this store indiscriminately: planning documents can contain private material. The source DOCX is not modified. No automatic Git upload or game application occurs.

Open the town style workspace, select a DOCX, enter scope instructions, run planning, review evidence and DSL in the plan panel, select representative objects, generate, then visually approve and apply. Plain prompt and Crypt workflows remain supported.

## Generalization experiments

Town vision requests now carry `mapId` (`town` or `harvest-village`). Extraction, source hashes, ground placement, approval and browser placement storage use that same map; unsupported maps are rejected. Harvest currently catalogs building annotations and complete reusable tree stamps from the shared tileset/LPC registry, with exact-pixel deduplication. Incomplete tree stamps and uncertain visual classifications remain unapproved/skipped. Other harvest props and terrain receive only the global atmosphere pass, not individual style generation. This is partial map coverage, not a claim of automatic arbitrary-object segmentation. Existing town profiles remain supported.

Geometry preservation does not freeze source RGB or lighting. Global palette/color-grading requests (including a darker palette) authorize nonzero theme palette blending. Explicit brightness-only requests or original-color preservation retain zero palette blending. Object-specific foliage palettes must not leak into building colors. Original alpha, dimensions and placement remain unchanged.

Ground-route DSL includes a requested object's defining silhouette and visible material texture, rather than only its name/color. The shared evidence audit rejects identity changes and invented accessories; conventional defining physical features are permitted. The renderer requests native-size readable texture clusters instead of smooth gradients. These are general prompt constraints, not object-specific templates, and semantic visual review remains mandatory.

After user approval, town generation distinguishes audited physical placement routes. Ground props use independent single-object English DSL, strict flat-background extraction, native 32x32 transparent sprites and conservative TMX ground anchors. They are not clipped to the host building alpha. Identical commands reuse the generated sprite within a run. Missing safe anchors block that object's decoration; no unsafe placement fallback is used. Attached decorations retain the existing registration and original-alpha constraints. Source geometry is never regenerated for ground decoration, and original recolor layers survive decoration failure. All results still require visual review; semantic/placement model audits are not proof of correctness.

Both input modes now enter the same evidence-based document Planner. Free text is split into sentence-level evidence blocks; uploaded DOCX retains its paragraphs. Normalization requests separate operations/scopes rather than combining lighting and prop changes. Global palette inference receives only normalized global color/state requirements, not the entire object-specific request. This prevents direct input leakage but still requires visual validation of the inferred palette. A zero recolor strength with an empty palette uses an inactive neutral palette; nonzero recoloring still requires a valid palette. Raw model responses are retained.

Physical routing receives original source quotations as well as generated commands to avoid treating outside/beside as attached-to-wall. It audits the route, rejects extra item types beyond the original command count, and deduplicates identical item commands. These checks do not replace visual review of the resulting sprite. `scripts/check-style-input-modes.py` exercises upload requirements and stale-document isolation with a mocked planning API; it does not generate images.

Ground commands must start with `Add one` to avoid plural prompts contradicting isolated-sprite extraction. The style reference is a nonempty original source closest to the native 32px size, rather than the host building; its ID and dimensions are recorded. This reduces host-geometry copying but does not guarantee semantic fidelity. No alpha/component thresholds are relaxed when generation fails.

`scripts/run-style-generalization-batch.py` runs three fixed independent-prop cases sequentially through the shared generation lock. `scripts/evaluate-document-generalization.py` separately saves one-pass automatic normalization and object plans for the actual document and explicitly synthetic winter/spring fixtures. Cached object labels and a neutral direction isolate document planning; these are not end-to-end recognition or theme accuracy benchmarks. Raw model responses and failed outputs are retained.

`scripts/compose-generalization-evaluation.py` produces offline town and harvest-village previews. Placement excludes TMX object-layer collisions, annotated objects, portal margins, and NPC homes/wander envelopes. A tile-connectivity check rejects placements that disconnect the baseline accessible region. Door approaches and blank wall anchors are heuristics, not semantic detection. Dynamic NPC paths, actual doors and runtime occlusion still require playtesting. The full-theme palette and reused autumn tree result are an explicitly assisted composition baseline, not an automatic document result. No source map or runtime selection is modified.
